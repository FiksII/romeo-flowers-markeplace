# Фото товаров в Beget S3

Приложение использует Django Storage API: новые фотографии магазина сохраняются в
S3 при `S3_ENABLED=True`. При выключенном флаге используется локальный `media/`.
База хранит относительное имя файла; шаблоны получают URL через `Listing.image_url`.
Миграций схемы для подключения S3 не требуется.

## Настройки

В локальном `.env` или серверном `/srv/romeo-marketplace/shared/runtime.env`:

```dotenv
S3_ENABLED=False
S3_BUCKET_NAME=fe3d692e570c-flowersstorage
S3_ENDPOINT_URL=https://s3.ru1.storage.beget.cloud
S3_REGION_NAME=ru1
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_LOCATION=media
S3_QUERYSTRING_AUTH=True
```

Заполните ключи из **реквизитов S3 этого бакета**. Ключи не добавляются в Git.
При включённом S3 приложение требует непустые имя бакета и оба ключа.
`InvalidAccessKeyId` означает, что сервис не распознал переданный идентификатор
ключа; проверьте реквизиты в панели Beget.

Регион `ru1` и адресация с бакетом в пути соответствуют
[инструкции Beget](https://beget.com/ru/kb/faq/cloud/podklyuchenie-s3-v-wordpress-i-nastrojka-hraneniya-izobrazhenij-v-nem).
Настройки передаются в
[django-storages](https://django-storages.readthedocs.io/en/latest/backends/amazon-S3.html)
через `STORAGES["default"]["OPTIONS"]`.

Файлы сохраняются под префиксом `media/`. ACL при загрузке не устанавливается.
По умолчанию URL подписан и действует час, поэтому открывать бакет для всего
интернета не требуется. Для публичного бакета можно задать
`S3_QUERYSTRING_AUTH=False`, предварительно настроив публичное чтение в Beget.
Права ключей должны разрешать загрузку, чтение, проверку существования и удаление
объектов в этом префиксе; проверка отсутствующего объекта также может требовать
права перечисления бакета. Приложение не меняет политику бакета.

Статика (`collectstatic`), оформление сайта и исходные демофото остаются в
репозитории. Загруженные фото имеют приоритет над демоизображениями.
Тестовые настройки принудительно используют локальное хранилище.

## Превью фото

Каталог, страница букета, корзина и таблица букетов кабинета показывают не
оригиналы, а превью sorl-thumbnail в WebP (`market/thumbnails.py`): 320×400,
400×500, 600×750 и 800×1000 для карточек (quality 75), 640×800 и 1000×1250
для страницы букета (quality 80), 100×125 и
200×250 для строк. Браузер выбирает размер по `srcset`. Превью создаётся при
первом показе фото и сохраняется в том же хранилище под `cache/` (в S3 —
`media/cache/`), записи о нём — в таблице `thumbnail_kvstore` и в кеше. Ссылки
выдаются через стабильные подписанные адреса `/photos/` на домене сайта.
Если превью сделать не удалось,
страница показывает оригинал.

sorl-thumbnail пересоздаёт хранилище по пути класса без аргументов, поэтому
бэкенд S3 — `market.storage.MediaS3Storage`: он сам берёт параметры из
`STORAGES["default"]["OPTIONS"]`. Новое фото партнёра получает новое имя и новые
превью; прежние превью остаются в `media/cache/` и сайту не мешают.

## Кеш фотографий и просмотр внутри сайта

При S3_ENABLED шаблоны превью и галереи используют `/photos/<token>/`.
Django Signer разрешает чтение только имени, подписанного приложением; это
не универсальный прокси внешних URL. Бакет остаётся закрытым. Фотографии
каталога доступны обладателю ссылки; адрес стабилен и не имеет часового срока.
Оригинальные S3 URL остаются в Storage API для интеграций мессенджеров.

Отдельный Django FileBasedCache `photos` хранит до 1000 записей на 30 дней.
На сервере `PHOTO_CACHE_DIR=/srv/romeo-marketplace/shared/photo-cache`, папка
0700 принадлежит приложению и расположена вне публичных media/static. Для
systemd требуется дополнительный `ReadWritePaths` ровно к этой папке.
Не размещать кеш в media: Caddy выдаёт media как публичные файлы.
Успешные ответы содержат public max-age=2592000, immutable и ETag; GET с
If-None-Match возвращает 304, HEAD не отправляет тело. Ошибки 404/412/503
не кешируются. Перед чтением проверяется ограничение объекта 8 МБ.

После подготовки релиза выполнить от пользователя приложения:

```sh
python manage.py warm_photo_cache --settings=romeo_market.preview_settings
```

Команда создаёт актуальные превью опубликованных букетов активных магазинов
и прогревает кеш, включая оригиналы для просмотра. Кеш общий между worker
процессами и релизами; очистка не удаляет S3-файлы. Фото с новым именем имеет
новый адрес и не подменяется старым кешем.

Нажатие на главное фото открывает встроенный HTML dialog с закрытием/Escape,
стрелками, свайпом и увеличением. Для одного фото диалог работает без пустых
кнопок перелистывания. Оригинал загружается при открытии; ошибки можно повторить.
При отключённом JavaScript остаётся обычная ссылка на фото того же домена.

## Перенос существующих фото

Перед включением S3 сохраните резервную копию БД и локальных файлов. Установите
`S3_ENABLED=True` в окружении команды переноса. При работающем сайте выполняйте
перенос и переключение приложения в окно обслуживания: существующие имена
файлов начнут указывать на S3 после перезапуска приложения.

Локальное демо, план переноса без записи файлов или изменения БД:

```powershell
uv run python manage.py migrate_listing_photos --include-seed --dry-run --settings=romeo_market.demo_settings
```

План показывает источники и будущие имена; он не проверяет доступ к S3.
Сам перенос:

```powershell
uv run python manage.py migrate_listing_photos --include-seed --settings=romeo_market.demo_settings
```

На опубликованном HTTPS-демо используйте настройки `romeo_market.preview_settings`,
пользователя приложения и актуальное серверное окружение:

```sh
python manage.py migrate_listing_photos --include-seed --source-dir /srv/romeo-marketplace/shared/media --settings=romeo_market.preview_settings
```

Без `--include-seed` копируются только ранее загруженные фотографии. Этот флаг
также переносит демофото каталога из `static/market/bouquets/` и записывает их
новые имена в поле `photo`. Остальные изображения оформления не переносятся.

Старые загрузки получают отдельные имена `listings/imported/<SHA-256>.<расширение>`,
чтобы перенос не записывал данные по пути новой загрузки партнёра. Исходное имя
меняется в БД только после успешной загрузки. Одинаковое содержимое при повторном
переносе получает тот же путь.

Команда сохраняет оригиналы. Повторный запуск использует уже перенесённые файлы;
если локальный источник доступен, сравнивает SHA-256. Другой файл с тем же именем
останавливает перенос. Запись `photo` обновляется после успешной загрузки;
изменение фото партнёром во время переноса не перезаписывается. При ошибке уже
скопированные фото остаются, а команду можно повторить после устранения причины.

После переноса перезапустите приложение и проверьте фотографию в каталоге и
новую загрузку в кабинете магазина. В Caddy статика продолжает обслуживаться
локально; фото интерфейса идут через кеш `/photos/`, а Storage API продолжает
использовать S3.

## Возврат к локальному хранилищу

Перед выключением S3 скопируйте **все** актуальные файлы из префикса `media/` в
`MEDIA_ROOT`, сохранив относительные пути после `media/`. Это относится и к
демофото в `listings/seed/`, и к новым загрузкам. Затем задайте
`S3_ENABLED=False` и перезапустите приложение. Простое выключение флага без
копирования сделает отсутствующие локально фотографии недоступными.
